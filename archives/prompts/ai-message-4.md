`HIT-L0-spec-v0_1_1.md`（再アップロード版）を確認しました。M属性の翻訳フラグが `T` から `L` に、T属性の電子的証明フラグが `C` から `V` に変更されています。この変更により、M属性とT属性で同じ英字が重複しなくなり、旧4.2.5や旧11.3が不要になった点は整合しています。

一方で、変更の反映漏れと、前回から残る点があります。

## 1. フラグ変更に伴う矛盾

**9.3 に旧フラグ `C` が残っている:** 9.3 は「T属性に `S`、`P`、`O`、`R`、`T`、`C` のいずれかを付与した場合」としています。T属性の電子的証明は `V` に変わったため、`C` を `V` にする必要があります。現状では、存在しないT属性フラグを参照しています。

**5.2 の組み合わせ表の列見出し:** 列見出しが `C`, `D`, `A`, `T`, `H` のままです。一方、行見出しは `L` に変わっています。4列目の見出しを `L` に直してください。

## 3. T属性の変更に関する問題点

**4.1.5 の追加は妥当:** 4.1.5 で、T属性の省略と `N` が等価であることが明記されました。前回指摘した曖昧さは解消しています。

**11.3 の格下げ:** 11.3 で、ローカライズ表記に正準形を併記することが「すべきである」から「してもよい」に変わりました。この場合、正準形のないローカライズ表記は、該当するプロファイルを知らない受領者には解読できません。設計原則の法域中立や国際的な互換性と緊張関係にあるため、意図的な変更でなければ「すべきである」に戻すことを勧めます。

**ローカライズ時の一意性の定めがない:** 旧11.3の削除により、プロファイルがフラグに割り当てる文字の一意性について、定めがなくなりました。少なくとも次の2点を11章に定めておくと、ローカライズ表記の解析が保証されます。
- 同じ属性内で、異なるフラグに同じ文字を割り当ててはならない。
- 数字や区切り文字（`-`、`/`）と衝突する文字を割り当ててはならない。

## 4. `O` の開示範囲の評価（コミットログで追跡できる前提）

結論として、6.3.1 の「受領者が入手できる状態」という要件は満たしうると評価します。ただし、所在の示し方に不足があります。

**AI生成の編集前版がコミットされていること:** `C9` の申告で、`O` が実質的に意味を持つのは、AIが出力した編集前の版です。これが人間の修正前に、独立したコミットとして記録されている必要があります。v0.1.0 の時点ですでに申告者の修正（ライセンスや著作権者名の変更）が加わっていた場合、AIの生の出力はコミットログに存在しないことになります。

**付録Aの所在に、コミットの識別子がない:** 現在の `O` の所在は草稿のみを指しています。8.2 は「開示対象: <所在>」の明記を求めていますが、「コミットログのどこか」では受領者が特定できません。次のいずれかを付録Aに記載すると、所在が明確になります。
- 該当するコミットのハッシュ
- タグ（例: `v0.1.0-ai-original`）

**履歴の保存性:** リポジトリの履歴は、force push や squash によって書き換えられる可能性があります。タグやリリースとして固定しておくと、開示の持続性が担保されます。

**ウェブ公開時の受領者:** `system-2.md` によると、本文書は GitHub のサイトで公開される前提です。サイトの閲覧者はコミットログに直接アクセスしません。また、ZIP形式でダウンロードした場合も履歴は失われます。9.3 の一体的な頒布を満たすには、付録Aの所在をリポジトリ上のコミットまたはタグへの絶対URLにしておくのが確実です。相対パスはサイト上で解決できない場合があります。

**`T` への波及:** 6.1 の `T` は「生成および編集の日時」の開示を求めています。コミットログはこれも記録しているため、付録Aの `T` の所在にコミットログを併記すれば、編集日時の開示もあわせて満たせます。
